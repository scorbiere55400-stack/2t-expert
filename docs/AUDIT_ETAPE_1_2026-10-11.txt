7. Opérations à suivre dans cet ordre pour clôturer l'étape
1) Terminer la mise à jour des dépendances ; exiger audit production sans alerte, tests et compilation réussis ; publier les corrections sur ce même site et vérifier le déploiement.
2) Réconcilier les sources GitHub et Sites sans écraser un historique ni l'ancien travail : comparer, conserver les divergences, puis établir un flux unique documenté. Cette opération reste à faire.
3) Ajouter une protection de branche et des contrôles obligatoires sur GitHub via les réglages d'administration adaptés. Les outils disponibles dans cet audit ne permettent pas de modifier ces réglages ni la visibilité du dépôt. Décider la visibilité selon le partage voulu, puis vérifier le résultat ; un dépôt public sans secrets n'est pas automatiquement une fuite de données utilisateurs.
4) Avec un compte utilisateur réel autorisé : ouvrir /admin ; sauvegarder un dossier, recharger, retrouver le dossier et l'exporter. Avec un second compte : prouver qu'il ne voit ni ne modifie le dossier du premier. Le service de test n'a pas d'identité utilisateur, donc ce parcours n'est pas vérifié en production.
5) Vérifier une sauvegarde complète D1 et restaurer une copie dans un environnement isolé ; établir fréquence, rétention et procédure. Le simple historique des versions du site ne sauvegarde pas les données D1.
6) Examiner l'autorisation administrateur actuellement fondée sur deux adresses email ; migrer vers des identifiants Site vérifiés quand les deux sessions utilisateur sont disponibles. Les identifiants de partage du compte ne doivent pas être supposés identiques aux identifiants injectés dans le Site.
7) Traiter Supabase : déterminer si ce service est encore nécessaire, puis réactiver et auditer si nécessaire ou retirer proprement ses références après confirmation de l'absence d'usage. Aucun effacement exécuté.
8) Définir la conservation des dossiers, retours, exemples et compteurs ; contrôler suppression et purge. Les compteurs historiques ne sont actuellement pas purgés dans le code inspecté.
9) La connexion et l'entraînement de l'IA viendront ensuite : clé dédiée côté serveur, plafond financier dans le compte API, appel réel et simulation de panne/quota. L'absence de clé n'est pas un défaut de confidentialité, mais bloque la validation du fonctionnement génératif.

Critère de fin : tous les contrôles de sécurité applicables réussis, sauvegarde restaurable vérifiée, flux de source unique établi, parcours privé confirmé, risques résiduels documentés. Aucun statut « entièrement autonome » ne doit être annoncé sur la base de cet audit partiel.

Contrôles supplémentaires
- Les six migrations SQL suivies s'appliquent dans une base SQLite temporaire vide ; elles créent neuf tables et les colonnes attendues pour MécaBot. La base live contient dix-sept tables : il existe donc des tables historiques supplémentaires à inventorier dans une future sauvegarde complète. Ce test ne constitue pas une restauration de D1.

- Les instructions données au modèle et le filtrage de sortie ne prouvent pas la justesse de ses réponses ; prévoir des évaluations de fiabilité et un mécanisme de validation avant toute évolution autonome des connaissances.
